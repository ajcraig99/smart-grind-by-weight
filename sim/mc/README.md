# Monte Carlo harness (`sim/mc/`)

Stress-tests the real grind controller running in the digital twin (`sim/out/host/grindsim`, see `sim/ARCHITECTURE.md`).
One command reruns everything and regenerates the report:

```bash
# once: build the simulator (needs sim/tools/fetch_deps.sh first)
cmake -S sim/host -B sim/out/host -G Ninja && ninja -C sim/out/host

python3 sim/mc/run_mc.py            # full run  -> sim/reports/montecarlo.md + SVGs
python3 sim/mc/run_mc.py --quick    # small N   -> sim/reports/quick/montecarlo.md (not committed)
python3 sim/mc/run_mc.py --reuse    # rebuild the report from the raw CSVs of the previous run (no grindsim)
python3 sim/mc/run_mc.py --emit-params sweep 100007   # print the sampled plant parameters of one sweep run
```

Standard library only (Python 3). Charts are hand-written SVG. `--jobs N` sets the parallelism (default 4).

## Outputs

| Path | Content |
|------|---------|
| `sim/reports/montecarlo.md` | The report: method, results, SAFETY cases, every failure with reproduction command |
| `sim/reports/*.svg` | Charts used by the report |
| `sim/reports/montecarlo_failures.csv` | One row per failing run with the fully expanded reproduction command |
| `sim/reports/sweep_params.csv` | Sampled plant parameters of every sweep run (raw output kept with the report) |
| `sim/mc/scenarios/*.json` | Scenario files (generated by `run_mc.py` from its catalogue; identical on every run) |
| `sim/mc/out/{full,quick}/` (gitignored) | Raw per-set CSVs (`raw/set_<set>.csv`), per-run `--params` files (`params/`), firmware logs of the fault runs (`logs/`), `run_info.json` (wall times) |

The report has no timestamps or wall times, so the same `grindsim` binary and the fixed seeds give a byte-identical report.

## Scenario sets

Seeds are fixed in `run_mc.py` (`SEED_BASE`). Every scenario file of a set uses seeds `base .. base+N-1`.

| Set | Files | Seeds per file (full / quick) | What it is |
|-----|-------|-------------------------------|-----------|
| nominal | `nominal.json` | 500 / 24 | Target 18.0 g, 22.0 g beans, purge discarded, default plant |
| sweep | `sweep.json` | 1000 / 40 | Plant parameters drawn uniformly in their sweep ranges; `hx711_sps`, `lc_counts_per_g`, `lc_baseline_code`, `hx711_settle_ms_80sps` and `lc_gain_error` held at default |
| sweep_gain | `sweep_gain.json` | 300 / 12 | As sweep but `lc_gain_error` also sampled (+-5 %) |
| purge_keep | `purge_keep.json` | 300 / 16 | Purge mode, CONTINUE pressed without touching the cup |
| prime | `prime.json` | 300 / 16 | Prime mode (`grinder_mode` 0) |
| sps80 | `sps80.json` (`--set hx711_sps=80`) | 300 / 16 | 80 SPS ADC; the firmware refuses to start the scale, see report section 3.10 |
| sps30 | `sps30.json` (`--set hx711_sps=30`) | 300 / 16 | Model-only extra: a conversion rate the firmware's validation accepts |
| targets | `target_09` .. `target_40` (8) | 60 / 4 | Targets 9, 12, 15, 18, 21, 25, 30, 40 g, beans = target + 4 g |
| rundry | `rundry_{discard,keep,prime}_b{17.0..22.0}` (30) | 30 / 3 | Single-dose run-dry: beans 17.0 to 22.0 g x purge discard / keep / prime |
| faults | `fault_<family>_<timing>` (+ `fault_beans10`) | 20 / 2 | 13 fault and user-action families at PREDICTIVE+0.5/2/5 s, PULSE_DECISION+0, four fixed random delays after START (and START+0 for the stuck relays, boot+0 for feed block) |

Fault families: `lc_disconnect`, `lc_stuck`, `lc_noise_burst_1s` (x20 for 1 s), `lc_noise_burst_perm` (x20 permanent, PREDICTIVE+2 s only),
`relay_stuck_on`, `relay_stuck_off`, `remove_cup`, `bump30`, `bump200`, `motor_stall` (permanent), `motor_stall_2s`, `feed_block`, `reset` (power-on reset via the scenario `reset` action).
Random delays are drawn once from `random.Random("mc-fault-delays-v1")` and written into the scenario files.

Sets with per-run parameters (sweep, sweep_gain) and the fault set run one `grindsim` process per seed (4 in parallel); the others use `grindsim --batch N --jobs 4`.

## Reproducing one run

Every failure row in the report has a command of the form

```bash
sim/out/host/grindsim --seed 100007 --scenario sim/mc/scenarios/sweep.json --params sim/mc/out/full/params/sweep/100007.json
```

`sim/mc/out/full/params/` is written by `run_mc.py`; if it is absent, regenerate one file with
`python3 sim/mc/run_mc.py --emit-params sweep 100007 > p.json`. Add `--summary s.csv --log log.txt --out run.csv` for the summary row, firmware log and 10 ms trace.

## Definitions (also in the report, section 2.3)

- Failure: result not `SUCCESS`, or |`err_true_g`| > 0.03 g (`GRIND_ACCURACY_TOLERANCE_G`), or a SAFETY tag.
- SAFETY-SIGNAL: `motor_invalid_signal_s` > 0.5 s or `motor_no_sample_s` > 0.5 s (0.5 s = the firmware's `has_recent_sample()` window).
- SAFETY-TIME: `motor_max_run_s` > 60 s (`GRIND_TIMEOUT_SEC`) or `motor_after_end_s` > 1.0 s (the 1.0 s is the report's own choice).

## Runtime

Measured on the 4-vCPU development VM (`--jobs 4`), one run per process at about 0.2 to 0.4 s wall each:

| Mode | Runs | Wall time |
|------|------|-----------|
| `--quick` | 436 (+ 2 per fault file) | about 30 s |
| full | 6300 | 338 s and 363 s in two consecutive runs (about 6 minutes) |

Memory and disk: the fault runs keep one firmware log each under `sim/mc/out/<mode>/logs/` (about 8 KB each, gitignored).

## Caveats

The plant is a model with many placeholder parameters (`sim/plant/ASSUMPTIONS_PLANT.md`). The report describes the model and the firmware logic, not any real grinder.
